# תוכנית ביצוע: קהילת WhatsApp חיה על Hermes

**סטטוס:** מקור האמת לביצוע  
**תאריך:** 2026-08-16  
**מחליף:** את מסלול הארכיון, החיפוש וה־profiles ב־`community-mode.md`

## 1. התוצאה שאנחנו בונים

תכל'ס הוא Hermes שמחובר למספר WhatsApp קהילתי:

- הוא נוכח בקבוצות שאושרו על ידי מנהל הקהילה.
- הוא שומר כל הודעה חדשה בקבוצות האלה, גם כשלא פנו אליו.
- שמירה פסיבית אינה מפעילה מודל, כלים, הקלדה, אישור קריאה או תשובה.
- כשפונים אליו בשם, בתיוג או בתגובה להודעה שלו — Hermes רץ ועונה בקבוצה.
- מידע שנאמר בקבוצה אחת ניתן לחיפוש ולניתוח כאשר שואלים בקבוצה אחרת.
- מנהל הקהילה מדבר עם Hermes בשפה טבעית; אין דשבורד ניהול קהילה.
- ה־UI של תכל'ס משמש רק למה ששיחה אינה יכולה לבצע היטב: QR, התחברות ספק,
  בחירת קבצים, אישורים חריגים ומצב תקינות.

דוגמאות קבלה:

1. נכתבו בקבוצת הספורט זמני הבריכה בלי לפנות לתכל'ס. מאוחר יותר תושב שואל
   בקבוצה הראשית "תכל'ס, מתי הבריכה פתוחה?" ומקבל תשובה עם מקור ותאריך.
2. מנהל שואל "כמה תושבים שונים התלוננו השבוע על התאורה?" ו־Hermes מחפש את
   ההודעות הרלוונטיות, מסביר את שיטת הספירה ומחזיר מספר שולחים ייחודיים.

## 2. הכרעות ארכיטקטורה

1. **Hermes הוא המנוע והמוח.** תכל'ס מוסיפה Skills, Plugin, קונפיגורציה ומשטחי
   מערכת קטנים; היא אינה בונה Agent Runtime, מסד שיחות או מערכת RAG חלופית.
2. **נשארים על Hermes הרשמי.** כל עבודה מתחילה מתג רשמי מאומת. שינויי מנוע
   נשלחים upstream ונישאים זמנית כתור patches קטן רק עד המיזוג.
3. **לא מוסיפים מסד נתונים.** הודעות נשמרות ב־`state.db` הקיים, בטבלת
   `messages`, ונכנסות אוטומטית לאינדקסי FTS של Hermes.
4. **‏`HERMES_HOME` אחד — עודכן 2026-08-16.** החלטת משתמש: אין שתי התקנות
   ואין שני בתים. תכל'ס הוא מעטפת שמכירה ל־Hermes היחיד את ההגדרות והכלים;
   יכולת הקהילה נוספת לאותו בית באמצעות profiles ,routes וגדרות בבעלות
   המחולל, בסמנטיקה additive שאינה דורסת פריסה עסקית קיימת. ה־observer
   הממתין ל־upstream מוחל כ־overlay זמני על ה־checkout הרשמי (editable),
   וה־updater מסרב לעדכן install נעוץ.
5. **ב־MVP יש corpus קהילתי משותף אחד.** כל הקבוצות הציבוריות המאושרות חולקות
   את אותו מאגר. לא נשענים כרגע על בידוד פיזי בין profiles, משום שה־gateway
   מחזיק SessionStore משותף והשער הזה אינו מוכח כגבול פרטיות.
6. **קבוצה רגישה אינה מצטרפת ל־MVP.** בהמשך היא תקבל פריסה נפרדת (מכונה או
   התקנה אחרת) או בידוד מנוע מוכח. לא מגינים עליה באמצעות prompt בלבד.
7. **ארכיון אינו אמת.** הודעת תושב היא ראיה היסטורית לא מאומתת. ידע מוסמך
   נוצר לפי מקור, עדכניות, סתירות וכללי קידום הידע בסעיף 7.
8. **לתושבים לא חושפים את `session_search` הגולמי.** הוא רחב מדי ואינו מספק
   ספירות מלאות. תכל'ס תספק כלי Hermes צר שמוגבל בשרת לקבוצות המאושרות.

## 3. זרימת הודעה אחת

```text
Baileys / WhatsApp
        │
        ▼
בדיקת קבוצה מאושרת + נרמול זהות
        │
        ▼
שמירה עמידה ב-state.db כ-observed
        │
        ├── ההודעה לא פנתה לתכל'ס ──► עצירה, ללא inference וללא outbound
        │
        └── ההודעה פנתה לתכל'ס
                 │
                 ▼
        Hermes + כלי הקהילה המורשים
                 │
                 ▼
             תשובה בקבוצה
```

סדר הפעולות מחייב: קודם שמירה, אחר כך החלטת dispatch. כשל בשמירה של הודעה
פסיבית לעולם אינו הופך אותה בטעות ל־turn של הסוכן. הודעה כפולה מזוהה לפי
`platform_message_id` ואינה נכתבת שוב.

כל הודעה נשמרת כשורה נפרדת עם:

- התוכן וסוג המדיה;
- זמן האירוע המקורי;
- מזהה קבוצה ושם קבוצה;
- מזהה שולח קנוני, LID/alias ושם תצוגה;
- `platform_message_id`;
- `observed=true` כאשר לא הופעלה כסיבת ה־turn;
- metadata מובנה ב־`display_metadata`, לא רק prefix טקסטואלי שנדרש לפרש.

ב־MVP נשמרים טקסט, כיתוב ומטא־דאטה של קובץ. תוכן בינארי של מדיה אינו נכנס
לארכיון כברירת מחדל.

## 4. מה ממחזרים מ־Hermes

- דפוס `observe_unmentioned_group_messages` של Telegram: session קבוצתי
  משותף, `observed=True`, שמירה ללא dispatch והצגת observed context בנפרד.
- `SessionStore` ו־`SessionDB` עבור sessions, messages, dedupe וריסטארט.
- אינדקסי FTS הקיימים עבור חיפוש מיידי.
- Profile/Skills/Toolsets עבור זהות והתנהגות הסוכן, אך לא כגבול DB ב־MVP.
- Cron ויכולות הסוכן עבור עיבוד ידע ברקע, רק לאחר שהארכיון אמין.
- מנגנוני QR, directory והגדרות WhatsApp שכבר קיימים בתכל'ס.

ה־business passive-ingest הוא חומר למיחזור ולבדיקות fail-closed, אך אינו
מועתק כפי שהוא: הוא שומר `user + NO_REPLY`, מפריד sessions לפי שולח ואינו
רואה הודעות שנעצרו בשער התיוג.

## 5. השינוי החסר במנוע: WhatsApp observer

יש לבצע port קטן מה־Telegram adapter אל WhatsApp:

1. להוסיף `observe_unmentioned_group_messages` ל־WhatsApp, כבוי כברירת מחדל.
2. להפעיל אותו רק עבור `group_allow_from` מפורש.
3. לבנות `MessageEvent` גם להודעה שנפלה רק ב־mention gate.
4. לחתום את ה־owning profile/home לפני כתיבה פסיבית.
5. לנתב הודעות observed והודעות trigger לאותו session קבוצתי משותף.
6. לשמור כל הודעה בנפרד עם metadata, זמן ו־message ID מקוריים.
7. להציג observed rows למודל כראיות רקע לא מהימנות, לא כבקשות לביצוע.
8. לעצור לפני Agent dispatch כאשר לא היה trigger.

PR ‏`#85490` נשאר בתוכנית, אבל עם חוזה מדויק: הוא מספק **הקשר שיחה מיידי**
ל־turn שהפעיל את הסוכן, כדי שהודעה כמו "אז מתי זה מתחיל?" לא תגיע למודל
מנותקת מן הפטפוט שקדם לה. הוא אינו בסיס הארכיון ואינו מוחלף על ידי ה־observer.

שני המנגנונים משלימים זה את זה:

- ה־observer שומר כל הודעה בנפרד ובאופן עמיד לצורך חיפוש, ניתוח וריסטארט.
- `#85490` מכניס חלון קצר של השיחה האחרונה ישירות ל־context של התשובה הנוכחית,
  בלי לחייב את Hermes לבצע קודם חיפוש יזום.

במהלך ה־port נשווה את חלון ה־50 לדרך שבה Telegram מציג observed rows כבלוק
context נפרד. אם שניהם מספקים אותו תוכן, נאחד את מסלול ההצגה כדי למנוע כפילות;
לא מסירים את `#85490` ולא משנים את התנהגותו בלי בדיקת parity מפורשת שמוכיחה
שהמודל עדיין מקבל את אותו הקשר מיידי.

## 6. כלי Hermes בטוח לחיפוש ולניתוח

נוסיף Plugin tool בשם פנימי `community_archive`. הכלי קורא את `state.db`
הקיים ואינו כותב אליו. ה־Skill מחליט מתי להשתמש בו; המשתמש אינו רואה טופס.

פעולות MVP:

- `search`: חיפוש מדופדף עם טווח תאריכים ותוצאות הכוללות מקור וזמן.
- `count`: ספירת הודעות או שולחים ייחודיים מתוך תוצאת חיפוש מוגדרת.
- `recent`: הודעות אחרונות לפי נושא לצורך בדיקת עדכניות או סתירה.

גבולות קשיחים:

- היקף הקהילה והקבוצות מוזרק בצד השרת מהקונפיגורציה.
- אין פרמטר `profile`, נתיב DB או אפשרות "all" שהמודל יכול להרחיב.
- פילטר קבוצה, אם יינתן, יכול רק לצמצם מתוך ה־allowlist.
- sessions של DM ניהולי, עסק או קהילה אחרת אינם מוחזרים.
- תוצאות observed מסומנות כתוכן לא מהימן ומכילות provenance.
- שאילתה כמותית מחזירה גם את מספר המועמדים והקריטריון; Hermes לא מציג
  ספירה סמנטית כמדויקת אם נדרש שיקול אנושי לסיווג "תלונה".

## 7. למידה דינמית בלי הרעלת ידע

הלמידה מתבצעת בשתי שכבות:

### שכבה א — retrieval מיידי

כל הודעה מאושרת ניתנת לחיפוש מיד. ברוב המקרים אין צורך לקטלג מראש: כשנשאלת
שאלה, Hermes מחפש, משווה עדכניות ומנסח תשובה עם מקור.

### שכבה ב — ידע קהילתי מוסמך

Hermes יכול לקדם עובדות שימושיות לידע מתמשך לפי הכללים הבאים:

- הודעה ממנהל או מערוץ רשמי יכולה להפוך אוטומטית למועמדת ידע.
- הודעת תושב רגילה נשארת ראיה בארכיון ואינה הופכת לבדה לעובדה מוסמכת.
- סתירה מול ידע קיים אינה נפתרת בשקט; Hermes מציג אותה למנהל.
- מידע רגיש או בעל השפעה גבוהה דורש אישור מפורש.
- כל עובדה שומרת מקור, זמן קליטה ותאריך תוקף כשיש כזה.

לא מפעילים LLM על כל הודעה. לאחר שה־MVP עובד, Cron של Hermes יכול לעבור
במנות על הודעות חדשות ממקורות רשמיים ולהציע או לבצע עדכוני ידע לפי הכללים.
זו גם ברירת המחדל היעילה: retrieval מתבצע רק כשיש שאלה; curator אחורי רץ
בתדירות נמוכה ורק על הדלתא מאז הריצה הקודמת. הידע הנגזר תמיד מפנה לשורות
המקור ב־`state.db`, ולכן אפשר לבטל או לבנות אותו מחדש בלי לאבד את הארכיון.

## 8. סדר העבודה

### שלב A — baseline וחוזה

- לקבע את התוכנית הזאת כמקור אמת.
- להפסיק להציג `history_backfill=50` כארכיון.
- לסמן את הנחת ה־DB הפר־profile הישנה כמבוטלת.
- לכתוב בדיקות קבלה נכשלות לפני שינוי המנוע.

**יציאה:** בדיקות מוכיחות שה־Hermes הרשמי אינו שומר unmentioned WhatsApp.

### שלב B — observer עמיד ב־WhatsApp

- לבצע את סעיף 5 בענף חדש שמבוסס על התג הרשמי המאומת.
- לשמור את `#85490` כמנגנון immediate context ולבדוק parity מול observed
  context של Telegram; כל איחוד יהיה פנימי בלבד ולא יוריד יכולת.
- להוסיף unit tests למותר/אסור, trigger, dedupe, timestamps, metadata וריסטארט.
- להוסיף בדיקה שבה הודעת trigger עמומה נענית נכון בזכות 50 הודעות הרקע
  האחרונות, בלי קריאת `community_archive`.
- לפתוח PR upstream ממוקד.

**יציאה:** הודעה שלא תייגה את הבוט נשמרת בנפרד, שורדת restart ואינה מפעילה
מודל או outbound; ובהפעלת הבוט המודל מקבל גם את ההקשר הקבוצתי המיידי.

### שלב C — כלי `community_archive`

- לבנות Plugin קטן מעל DB קיים.
- לאכוף scope בשרת ולבדוק שאין קריאה ל־DM, עסק או קהילה אחרת.
- להוסיף search, pagination, count ו־unique senders.

**יציאה:** Hermes מוצא מידע חוצה קבוצות ומבצע ספירה דטרמיניסטית על קבוצות
מורשות בלבד.

### שלב D — חיבור מצב הקהילה

- לפשט את generator ל־community home/corpus אחד עבור קבוצות ציבוריות.
- להתקין observer config, Plugin ו־Skills דרך provisioning הקיים.
- להסיר `session_search` הגולמי מה־toolset של התושבים.
- להשאיר את ניהול הקהילה כשיחה עם Hermes המלא של תכל'ס.

**יציאה:** התקנה חדשה עובדת ללא עריכת YAML/JID ידנית וללא dashboard קהילה.

### שלב E — בדיקה חיה

- לחבר מספר ייעודי וקבוצות בדיקה אמיתיות.
- להוכיח את מטריצת הקבלה בסעיף 9 ולשמור ראיות.
- לבצע restart באמצע הבדיקה ולהוכיח שאין אובדן.

**יציאה:** שאלת זמני הבריכה וספירת תלונות עובדות מקצה לקצה.

### שלב F — למידה מוסמכת והיסטוריה ישנה

- להוסיף Skill/Cron לקידום עובדות ממקורות רשמיים.
- לבנות importer ל־Export Chat שמשתמש באותו schema ו־dedupe.
- להוסיף retention, revoke/delete ו־opt-out לפני פריסה אמיתית רחבה.

**יציאה:** ידע מתעדכן אוטומטית עם provenance, והיסטוריה ישנה נכנסת בלי מסלול
אחסון מקביל.

## 9. מטריצת קבלה מחייבת

| תרחיש | תוצאה נדרשת |
|---|---|
| הודעה רגילה בקבוצה מאושרת | נשמרת פעם אחת; 0 inference; 0 outbound |
| הודעה בקבוצה לא מאושרת | אינה נשמרת ואינה מפעילה דבר |
| תיוג/מילת השכמה/תגובה לבוט | נשמרת ומפעילה תשובה אחת |
| שאלת המשך עמומה אחרי פטפוט קבוצתי | המודל מקבל את חלון ההקשר האחרון בלי חיפוש יזום |
| restart אחרי הודעה פסיבית | ההודעה עדיין searchable |
| אותה הודעה נשלחת שוב מהגשר | dedupe לפי `platform_message_id` |
| מידע בקבוצה א', שאלה בקבוצה ב' | Hermes מוצא אותו עם מקור וזמן |
| שלושה שולחים מתלוננים, אחד פעמיים | `count unique senders` מחזיר 3 |
| prompt injection בתוך קבוצה | נשמר כראיה; אינו מבצע הוראה |
| resident מבקש היסטוריית מנהל/עסק | הכלי מסרב ואינו מחזיר נתונים |
| ידע חדש סותר ידע קיים | Hermes מציג סתירה; אינו דורס בשקט |

## 10. אספקת מנוע ועדכונים

- Business ממשיך להשתמש במהדורת Hermes הרשמית האחרונה שעברה תאימות.
- פיתוח observer נעשה מענף שנוצר מהתג הרשמי, לא מענף fork מתמשך.
- כל שינוי מנוע מקבל PR upstream ובדיקות חוזה בתכל'ס.
- עד שה־PR מוזג, הפיילוט רשאי להשתמש בתור patches מינימלי ומתועד מעל אותו תג.
- אם נדרש release לפני המיזוג, מפרסמים tag זמני אחד עם base רשמי ו־patch SHAs
  במניפסט; לא מעדכנים מ־`main` ולא אוספים תיקונים לא קשורים.
- לאחר מיזוג upstream מוחקים את ה־patch מהתור וחוזרים לתג הרשמי בלבד.

## 11. מה לא בונים

- לא DB נוסף, vector store או RAG עצמאי.
- לא שירות ingestion נפרד מ־Hermes.
- לא dashboard לניהול קבוצות או ידע.
- לא inference על כל הודעת קבוצה.
- לא אמון אוטומטי בכל הודעה שנשמרה.
- לא הרשאות שמבוססות רק על SOUL/System Prompt.
- לא בידוד קבוצות רגישות על בסיס profile עד שה־DB והחיפוש נאכפים בפועל.

## 12. Definition of Done ל־MVP

ה־MVP הושלם רק כאשר שלבים A–E עברו וכל תרחישי סעיף 9 הוכחו, כולל restart
וחסימת מידע מחוץ ל־scope. שלב F הוא השלב הבא של המוצר, אך אינו תנאי לכך
שהסוכן "חי" בקבוצות: כבר ב־MVP הוא אוסף הכול, מחפש בין קבוצות ומנתח לפי
בקשה באמצעות Hermes.
